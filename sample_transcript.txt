Professor: All right, hi everyone. Today we are going to talk about hash maps and hashing functions. This is a really important topic and it will show up on the exam. Make sure you have your notes open.
Professor: Let's start with the basic idea. A hash map is a data structure that stores key-value pairs. Instead of scanning every element to find what you need, we use a hashing function to compute exactly where in memory a value lives. This gives us average O(1) lookup time, which is extremely fast.
Professor: A hashing function takes a key — could be a string, an integer, anything — and maps it to an index in an underlying array. The simplest version is key modulo the size of the array. So if the array has 10 slots and the key is 23, the hash is 23 mod 10, which is 3. You store the value at slot 3.
Student: What happens if two keys hash to the same index?
Professor: That is called a collision, and it is the central challenge of hashing. There are two main strategies. The first is chaining, where each slot holds a linked list of all entries that hash there. The second is open addressing, where if a slot is taken you probe for the next available one.
Professor: Chaining is simpler to implement and handles high load factors better, but uses extra memory for the linked list pointers. Open addressing keeps everything inside the array and is more cache-friendly, but performance degrades quickly as the table fills up. Python's built-in dict uses a variant of open addressing.
Student: What makes a good hashing function? Is modulo always enough?
Professor: Modulo alone is not great in practice. A good hashing function distributes keys as uniformly as possible to minimize collisions. If your keys have patterns — say they are all even numbers and your array size is also even — modulo will cluster them badly. A better approach is to use a prime number as your array size and mix the bits of the key.
Professor: For strings, a common approach is polynomial rolling hash. You treat each character as a digit in some base, multiply and accumulate, and take modulo at the end. For the string 'cat' you might compute c times 31 squared plus a times 31 plus t, all mod the table size. The base 31 is chosen because it is prime and works well for lowercase letters.
Student: Does the load factor matter a lot? When should you resize?
Professor: Yes, load factor is critical. It is defined as the number of entries divided by the number of slots. As it approaches 1, collisions become much more frequent and your O(1) guarantee breaks down. Most implementations resize — typically doubling the array — when the load factor exceeds around 0.7. Resizing requires rehashing every key into the new array, which is O(n), but it happens rarely enough that the amortized cost per insertion is still O(1).
Professor: One more thing worth mentioning is cryptographic versus non-cryptographic hash functions. Everything we have discussed is non-cryptographic — designed purely for speed and uniform distribution. Cryptographic hash functions like SHA-256 add the requirement that it should be infeasible to reverse the hash or find two inputs that produce the same output. Databases use non-cryptographic hashing for indexing. Security systems use cryptographic hashing for storing passwords.
Student: So hash indexes in databases work the same way as hash maps in memory?
Professor: Exactly. A hash index in a database is essentially a hash map where the keys are column values and the values are pointers to rows on disk. This makes equality lookups like WHERE id = 42 extremely fast. But hash indexes are useless for range queries like WHERE id BETWEEN 10 AND 50, because hashing destroys the ordering of keys. For range queries you need a B-tree index, which preserves order.
